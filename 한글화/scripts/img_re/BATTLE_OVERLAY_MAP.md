# 전투 애니메이션 오버레이 맵 (LANG1.BIN) — 세션13 실측

**목적**: gen_classnames(병종명 한글화)가 **물리 전투 애니메이션**에서만 프리즈하는 원인 =
게임이 전투 애니메이션 진입 시 **특정 RAM 구간에 전투 코드를 오버레이(단계 로드)** 하는데,
그 구간이 내가 conv 테이블·케이브를 넣은 자리와 겹친다. (마법 애니메이션은 이 오버레이를
안 써서 멀쩡 — 사용자 관찰로 확증.)

## 캡처 방법 (재현)
- 크래시 빌드(`KR_CLASSNAMES=1`)로 물리 전투 애니메이션 진입 → PC 정지/프리즈(CHCTLA=0x10 =
  NBG0 8bpp 확인) → `dump_memory` 로 workramh 통째로.
- 분석: `workramh[0x10000 + i]` (RAM 0x06010000+i = LANG1.BIN 상) 를 **원본 LANG1.BIN** 및
  **패치 LANG1.BIN** 과 3-way 비교. `ram != patched and ram != orig` = 오버레이.
- 스크립트: `scratchpad/overlay_map.py`, `overlay_map2.py` (dump = `scratchpad/dump_anim_crash/`).
  ※ dump는 세션별 scratchpad라 휘발 — 재개 시 위 방법으로 다시 뜬다.

   프리미티브/분류부 사이트도 1~2B씩 덮임 → 그 훅들도 위험.

## 다음 세션 실행계획 (병종명 배틀-세이프 재배치)
1. **conv_new(변환테이블 512B) + 케이브 전부(~800B)를 배틀-세이프 구간으로 이전.**
   - 1순위: `0x6306d-0x64097`(4138B) 또는 `0x64098-0x64b1c`(2692B) — 단, **원본이 데이터인지
     dead인지 확인**(현재 스크립트는 zero-run만 dead로 봄; 이 구간은 non-zero라 게임이 쓰는
     데이터일 수 있음 → 쓰면 다른 화면 깨질 위험. **오버레이-세이프 ≠ free**. 실제 free 여부는
     "그 바이트가 어디서 참조되나"를 별도 확인해야 안전).
   - 진짜 데드존(원본0)은 0x64c94-0x64e30의 ~407B뿐 → conv+케이브(~1312B) 다 넣기엔 부족.
     → **BIN 다른 데드존 탐색** 또는 **케이브 축소**(dual 프린터 훅 3개를 하나로 공유 등) 필요.
2. **프리미티브/분류부 사이트 자체(0xbedc/0xc03e/0x24b7a/0x24cc0/0x2c7ee/0x2c808)도 1~2B씩
   오버레이에 덮인다** → 그 12B 점프 패치가 전투 중 깨질 수 있음. 사이트 이전은 불가(고정 코드
   위치)이므로, **전투 중엔 그 훅이 실행 안 되도록** 하거나(현 씬가드가 그 역할이지만 케이브가
   깨지면 씬가드 도달 전 크래시), 애초에 **케이브를 세이프 구간에 두면** 사이트 12B가 1B 덮여도
   점프 리터럴(주소)만 온전하면 될 수 있음(리터럴 위치 확인 필요).
3. 재배치 후 **반드시 물리 전투 애니메이션까지 몰아 A/B 검증**(마법만 되는 걸로 착각 말 것).
4. 통과하면 `KR_CLASSNAMES=1` 기본화 복귀 → 8px HUD(`KR_HUD8=1`)도 같은 세이프 구간 논리로 재개.

## 참고
- 원본 disc A/B 폴더: `build/disc-orig/`(make_orig_disc.py). 검증에 상비.
- CHCTLA(0x25F80028)는 physical 미구현이라 직접 read 불가 — get_state g3.CHCTLA 로만 확인.
- Mednafen pause(P키)·exec BP는 캡처에 못 씀(HANDOFF 세션13 참조). 크래시 프리즈가 유일 신뢰법.
