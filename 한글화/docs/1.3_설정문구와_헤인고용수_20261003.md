## 2026-10-10 배포 반영 완료

사용자 요청으로 아래 문구 수정을 현재 한글판·개조판 BIN/CUE와 `1.3V`의 두 CHD, `1.3V 패치`의 두 xdelta·ZIP에 모두 반영했다. 10월 3일 전체 빌드의 입력 해시가 현재 소스·번역·폰트·원본과 정확히 같음을 확인한 뒤 기본 빌드에 반영하고 개조 빌드를 실행했다.

두 판 모두 이전 배포본과의 차이는 L1·L2 설정 라벨 각 3바이트 및 두 섹터의 검사값뿐이다. 크라운·룬스톤 개조 구성과 용병 고용 코드는 유지했다. CHD 무결성·6개 트랙 재추출·트랙 배치, 원본 복사본에서 두 패치 설치, ZIP 전체 내용 검사가 통과했다. 실제 에뮬레이터 게임 화면은 검사하지 않았다.

## 설정 문구: 수정 및 별도 전체 빌드 완료

제보: 게임 설정에서 `게임설정 / 표시설정 / 전투시xx / PCM / 고속전투` 중 일본어가 남음.

`scripts/img_re/patch_katakana_redirect.py`에서 해당 라벨만 **전투표시**로 바꿨다. 이미 존재하는 `전/투/표/시` 글자 참조를 재사용하며 공용 글꼴은 바꾸지 않는다.

- LANG1.BIN `0x2A7AC`, LANG2.BIN `0x2C4E8`.
- `3c 3d 06 2f 3f 70` → `3c 3d 41 42 70 70`.
- 원본 바이트가 다르면 기존 `_apply` 검사에서 중단한다.

## 헤인: 프리스트 3부대는 기본 경로와 일치, 팰러딘 3부대 제보는 미확정

사용자는 용병 종류가 아니라 **최대 고용 수 3부대**라고 확인했다. 이후 팰러딘 때도 3이었던 것 같다고 덧붙였다.

배포된 1.3에서 직접 확인한 내용:

- 헤인 이름 ID는 5. 기본 초기 직업은 워록 14, 초기 저장 고용 수는 3이다.
- 실제 전직표는 `LANG2.BIN 0x6527C + 이름 ID × 4`의 포인터가 가리키는 3바이트 행이다. 헤인의 워록 → 팰러딘은 14 → 38, 팰러딘 → 프리스트는 38 → 239이다.
- 팰러딘 38의 고용 수 증감은 +1, 프리스트 239는 −1이다.
- 전직 계산은 저장된 수에 해당 증감을 더하고 0 미만이면 0으로 만든다 (`0x31FAE–0x31FC7`).
- 고용 화면은 저장된 수를 읽어 3~6으로 제한해 표시한다 (`0x2B370–0x2B38D`). 내부 저장값 자체가 3 미만일 수 있다.
- 직업표 전체, 초기 설정 코드·헤인 초기값, 전직 수치 계산, 고용 수 표시 계산은 일본어 원본과 바이트 단위로 같았다.
- 기존 1.3의 `4A 06 02` 사건 명령 수정과 일반 전직의 고용 수 증감은 별도 경로다.

원본과 1.3의 실제 기계어를 작은 실행 검사기로 돌려 다음을 대조했다. 입력 저장값은 합성한 것으로 사용자 세이브를 읽은 결과가 아니다.

| 팰러딘 전 저장값 | 팰러딘 저장값 / 고용 한도 | 프리스트 저장값 / 고용 한도 |
|---:|---:|---:|
| 0 | 1 / 3 | 0 / 3 |
| 1 | 2 / 3 | 1 / 3 |
| 2 | 3 / 3 | 2 / 3 |
| 3 (기본 초기값) | 4 / 4 | 3 / 3 |
| 5 | 6 / 6 | 5 / 5 |
| 6 | 7 / 6 | 6 / 6 |

따라서 다른 변동 없이 처음 워록 → 팰러딘 → 프리스트로 육성하면 3 → 4 → 3이 계산된다. **팰러딘도 3이었다는 제보까지 정상이라고 확정하지 않는다.** 전직 전 저장값이 낮았는지 실제 세이브 확인이 필요하다. 고용 관련 코드나 밸런스 수치는 이번에 수정하지 않았다. 새 게임 시작 버전과 룬스톤 이력은 아래 후속 답변으로 확인했다.

검사 자료: `분석/1.3버그제보_20261003/verify_report.py`, `verification.json`, `rebuild.log`, `L1_menu_before_after.png`, `L2_menu_before_after.png`.

당시 검사 명령: `한글화/.venv/Scripts/python.exe -B 분석/1.3버그제보_20261003/verify_report.py`. 이 스크립트는 수정 전 기본 빌드·배포 manifest를 전제로 한다. 현재 배포 후 문구 변경 비교는 `분석/1.3문구수정배포_20261010/verify_menu_delta.py`, 개조 구성 검사는 같은 폴더의 `verify_profile.py`를 사용한다.

## 후속 제보: 개조판 새 게임, 룬스톤 미사용, 엘윈 로드도 3부대

사용자는 **1.3 개조판에서 새 게임으로 시작했고 룬스톤을 사용하지 않았다**고 확인했다. 엘윈도 워록에서 로드로 전직했을 때 고용 수가 3이었다고 알렸다. 이전 버전 세이브와 룬스톤 사용을 이 제보의 원인으로 설명하지 않는다.

실제 `1.3V/랑그릿사 I&II 1.3V 개조판.chd`를 새 조사 파일로 해제했다. CHD 해시는 배포 기록의 `8cca99eaa4d318e7d689e2f456ce3466bbd0ecc8823bcebacecf809c7ae4287f`, 추출한 첫 트랙은 배포 manifest의 `3ee34e77b08a4ccb2a940a12d50e95f602bd40113e268d7283ac0e06ae2dd2d5`와 일치했다.

이 파일과 일본어 원본에서 다음 경로를 실행해 비교했다.

1. 실제 새 게임 개인 기록 초기화 함수: 19명 초기값 생성. 엘윈 초기 내부 고용 수는 **4**, 헤인은 **3**이다.
2. 메이킹 기록의 선택: 후퇴한다 → 존재하지 않는다 → 자신의 힘 → 정찰대를 구하러 간다 → 통솔력 → 강대한 힘 → 소수정예 부대 → 사랑하는 사람을 지키려고.
3. 실제 선택 분기·호출·복귀 명령 및 능력치 변경 명령 실행. 워록 선택에서 **4 → 3**, 소수정예에서 **3 → 2**. 메이킹 후 다른 18명 기록은 보존된다.
4. 전체 전직 후보 선택·확정·수치 반영 함수 실행. 엘윈은 **내부 2 → 로드 3**, 고용 표시 계산은 **3 → 3**이다.
5. 헤인은 **내부/표시 3 → 팰러딘 4 → 프리스트 3**이다. 헤인의 두 전직 사이에는 원래 비주인공 개인 기록 동기화 함수도 실행했다.

일본어 원본과 배포 개조판에서 모든 위 결과가 같았다. 메이킹 명령 데이터와 직업표 전체도 원본과 같다. 원래 고용 화면은 내부 값이 2여도 최소 3을 표시하므로, 이 메이킹 경로라면 새 게임·룬스톤 미사용 상태에서도 엘윈 로드 전직 전후가 모두 3으로 보인다.

이번 플레이에서 메이킹을 이전 기록과 동일하게 선택했는지는 사용자에게 추가 확인 중이다. 헤인의 팰러딘 3부대 제보는 아직 재현되지 않았으며, 엘윈 결과를 근거로 함께 정상 처리하지 않는다.

한계: 초기화의 메모리 채우기는 대역, 선택 입력은 주입값이다. 질문·아이템 획득 표시, 전직 화면 그리기·일부 서비스는 생략 또는 대역 처리했다. 실제 기계어로 수치·분기·복귀를 검사했지만 에뮬레이터 화면, 사용자 세이브, 장치 저장 검사는 아니다. 엘윈의 전직 뒤 별도 저장 동기화 경로 전체는 이번 검사에 포함하지 않았다. 게임 코드는 추가 변경하지 않았다.
