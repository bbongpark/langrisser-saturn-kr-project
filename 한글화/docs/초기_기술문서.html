1프로젝트 개요와 결과

대상: 랑그릿사 I&II 드라마틱 에디션(세가 새턴, 일본판). 한 디스크에 1편(Ep1)과 2편(Ep2)이 들어 있는 합본으로, 텍스트 엔진은 두 편이 거의 동일하고 데이터 파일(LANG1.* / LANG2.*)만 분리돼 있습니다.

목표: 원본 게임 엔진을 개조하지 않고(=크래시 위험 최소화), 데이터 패치와 최소 바이트 패치만으로 게임 내 모든 텍스트를 한글로 렌더합니다. 번역 기준은 스팀 리메이크판(공식 한글)의 어조·용어입니다.

2개발 환경

  • 빌드 툴체인: Python 3.14 + Pillow 12. 전 과정이 순수 파이썬 스크립트(scripts/).
  • 폰트: Neo둥근모(neodgm.ttf, OFL 라이선스, 재배포 가능) — 16px 저해상도 가독성 우수.
  • 에뮬레이터/디버거: Mednafen 포크(Saturn, --enable-debugger) + 자체 제작 emucap MCP 제어 도구(Rust). 실행 중인 새턴 RAM·VRAM·레지스터를 라이브로 읽고 쓰며 브레이크포인트·세이브스테이트를 제어.
  • 플랫폼: 리눅스 네이티브(WSL 아님). 원본 ROM은 Track1 SHA-1로 무결성 검증.

3텍스트 엔진 역공학

3.1 인코딩과 폰트

본문 텍스트는 Shift-JIS입니다(타일 인덱스 커스텀 인코딩이 아님). 폰트 FONT.DAT는 비압축 1bpp 16×16 글리프를 JIS 코드 순서로 7개 블록에 담습니다:

블록글리프 수내용
0~3~500기호·구두점·숫자·영문·히라가나·가타카나
44,418JIS 한자(레벨1+2) — 한글 재할당의 주 대상
51,978추가 한자/외자

게임은 SJIS 코드를 표준 JIS 구·점으로 변환해 폰트 시트를 직접 인덱싱합니다(별도 커스텀 룩업 없음). 이 규칙이 확정돼 있어, 한글 글리프를 한자 슬롯에 넣고 그 SJIS 코드로 인코딩하면 엔진 무수정으로 한글이 렌더됩니다.

3.2 SCEN.DAT — 재귀 오프셋 트리

SCEN.DAT는 재귀적인 32비트 빅엔디안 오프셋 테이블 트리 + SJIS 문자열입니다. 대사·나레이션·조건·UI가 모두 이 안의 리프(leaf) 노드에 들어 있습니다. 무손실 파서/리패커(scen_tool.py, scen_repack.py)를 구현했고 라운드트립 테스트를 통과합니다.

3.3 제어코드

텍스트 스트림 안의 <0x0A 값은 제어코드입니다(정적 빈도 통계 + 최소 대립쌍으로 규명):

코드의미번역 처리
[NAME:XX] (09 XX)캐릭터 이름 변수 삽입반드시 보존
{04:XX}MTE 압축(일본어 어미/단어 확장, 201종)버림(한글은 전문 작성)
{06}{07}대화창/페이지 전환보존·활용
{08} / {02}창 내 줄바꿈보존
{01}(원본 미사용) → 반각 공백으로 재활용5장 참조

이름 테이블은 LANG1_SCEN.DAT @0x1407의 NUL 구분 배열(52명 전량 추출). [NAME:XX] 인덱스가 이 순서에 대응합니다.

핵심 함의: 원본은 {04} MTE로 일본어를 압축해 저장하지만, 한글은 이 압축을 쓸 수 없어 번역문이 원문보다 길어지기 쉽습니다. 그런데 패치는 파일을 늘릴 수 없는 제자리(in-place) 바이트 예산을 지켜야 합니다. 이 긴장이 5장의 여러 기법(반각 공백·페이지 넘김·한글 MTE·정렬보존 리빌드)을 낳은 근본 원인입니다.

4한글 폰트·인코딩 설계

4.1 한자코드 재할당 (완성형)

KS X 1001 완성형 음절을 한자 블록[4]/[5]의 빈/저빈도 슬롯에 배치합니다(kr_encoding.py). 번역 코퍼스에서 실제 쓰이는 고유 음절만 빈도순으로 수집해 동적으로 코드를 배정(build_table())하고, Neo둥근모 글리프를 그 슬롯에 굽습니다(patch_font()). 필요 음절 ≤2,350 < 공급 6,396 슬롯이라 병목이 없습니다.

4.2 좌우 절반 스왑 (필수 보정)

게임의 16×16 렌더러는 글리프의 왼쪽 8px과 오른쪽 8px 절반을 스왑해 읽습니다(원본 폰트가 스왑 저장돼 있어 렌더러가 되돌리는 구조). 이를 모르고 구우면 "데 → ㅔㄷ"처럼 자·모가 좌우로 어긋나 깨집니다. 따라서 한글 글리프를 구울 때 각 행의 좌8px·우8px 바이트를 미리 서로 바꿔 저장합니다(SWAP_HALVES).

4.3 한글 MTE 압축

일본어 MTE 사전 슬롯(죽은 슬롯)에 자주 쓰이는 한글 조각을 심어 대사를 압축하는 kr_mte.py를 구현했습니다. 바이트 예산이 빡빡한 블록을 이 방식으로 해소합니다.

5렌더링 제약 우회 핵심 기법

이 게임의 두 벽 — ① 16px 고정폭 렌더(반각 경로 없음)와 ② 늘릴 수 없는 바이트 예산 — 을 코드 훅 없이(데이터 또는 최소 패치만으로) 우회한 방법들입니다. 극도로 packed된 이 게임에서 상주 코드훅은 어느 위치든 크래시하기 때문에, "게임이 이미 가진 경로를 재활용"하는 것이 전 기법의 공통 전략입니다.

5.1 공백을 반각(8px)으로 만드는 방법

문제 단어 사이 띄어쓰기를 전각 공백으로 넣으면 공백 하나당 16px을 소모합니다. 좁은 대화창(가로 14칸)에서는 이 낭비가 커, 한 줄에 들어갈 글자 수가 크게 줄어듭니다.

해법 대사에서 실제로 쓰이지 않는 제어코드 {01}을 "반각 전진" 용도로 재활용했습니다. 렌더러에 18바이트짜리 최소 패치를 넣어, {01}을 만나면 커서 좌표 변수를 딱 한 타일(+8px)만 전진시키도록 했습니다(글자는 안 그리고 위치만 이동).

항목내용
재활용한 코드{01} — 원본 대사에서 미사용
렌더러 패치 위치LANG1.BIN 0x1b1fe (Ep2는 LANG2.BIN 0x1cee6), 18바이트
동작{01} → 커서 변수 [0x0609ab44]/[0x0609ab4c]에 +8px(한 타일)
텍스트 처리번역문의 모든 일반 공백을 {01}로 치환
return out.replace(' ', '{01}')   # 공백 하나가 16px → 8px
왜 코드 훅이 아니라 18바이트 패치인가: 실행 코드가 극도로 빽빽하게 채워져 있어 상주 코드 훅을 넣을 빈 공간이 사실상 없습니다(빈 영역 대부분이 게임 진행 중 스크래치로 재사용됨 → 훅 넣으면 크래시). 그래서 기존 렌더러 분기 안의 미사용 코드 자리에 딱 맞는 18바이트만 덮어써 안전하게 반각 전진을 구현했습니다.

5.2 페이지를 넘겨가며 써서 길이 제약을 줄이는 방법

문제 대화창은 가로 14칸 × 세로 3줄 = 한 페이지가 물리적 한계입니다. 한글 번역문은 원문보다 길어지기 쉬운데, 한 페이지에 욱여넣으면 화면 밖으로 넘치거나 바이트 예산을 초과합니다.

해법 게임이 원래 극적 연출용으로 쓰던 페이지 전환 제어코드 {06}{07} (원본에 약 640회 등장)를 번역문에도 적극 삽입했습니다. 긴 문장을 문장 경계에서 끊어 다음 페이지로 이어 쓰면, "한 페이지 = 3줄" 제약이 사실상 풀립니다. 번역자는 의미 단위로 {06}{07}만 넣고, render()가 나머지 포맷팅을 자동 처리합니다:

WIDTH = 14                          # 한 줄 14칸

def render(kr):
    pages = kr.split('{06}{07}')     # ① 번역자가 넣은 페이지 경계로 분할
    out_pages = []
    for p in pages:
        lines  = wrap_page(p)        # ② 14칸 기준 단어 단위 줄바꿈
        chunks = [lines[i:i+3] for i in range(0, len(lines), 3)]  # ③ 3줄씩 페이지로
        for ch in chunks:
            body  = '{08}'.join(ch)  # ④ 창 안 줄바꿈은 {08}
            first = (len(out_pages) == 0)
            # ⑤ 이어지는 페이지 첫 줄엔 빈 줄 보정(　{08})
            out_pages.append(body if first else '　{08}' + body)
    out = '{06}{07}'.join(out_pages)
    return out.replace(' ', '{01}')  # ⑥ 공백은 반각(5.1)
제어코드역할
{06}{07}대화창/페이지 전환 (버튼 눌러 다음 페이지)
{08}창 안에서 줄바꿈 (한 페이지 내 1→2→3줄)
　{08}이어지는 페이지 첫 줄 빈 줄 보정(연출 정렬용)
{01}반각 띄어쓰기 (5.1)

실제 예시 — 원문 한 덩어리를 두 페이지로 흐르게:

"놀라시는 것도 당연합니다.{06}{07}이 근방은 도적이 많아 무척 위험하니까요."
 └─ 1페이지 ──────────────┘         └─ 2페이지로 이어짐 ──────────┘
핵심: "한 창에 다 넣겠다"가 아니라 "넘겨가며 나눠 쓴다"로 발상을 바꾼 것이 포인트입니다. 페이지 추가는 바이트 예산 안에서 제어코드 몇 개만 더하면 되므로, 파일 크기를 그대로 두면서 길이 제약을 사실상 무력화합니다.

5.3 정렬보존 SCEN 리빌드

번역으로 리프 길이가 바뀌어도 SCEN 총 크기를 불변으로 유지하는 리빌더(rebuild_scen_with)입니다. 최상위 블록을 고정 정렬 오프셋에 두고, 각 블록의 0x00 패딩 리프로 성장/축소를 흡수합니다. 덕분에 디스크 LBA 재배치 없이 제자리(in-place) 덮어쓰기가 가능합니다(Ep1 SCEN 659,456B / Ep2 4,517,888B 고정).

6번역 파이프라인

6.1 번역 기준 (스팀판)

대사·나레이션·승패조건·제목·고유명사는 스팀 리메이크판(공식 한글)의 어조·용어를 기준으로 채택·재번역합니다. 참고자료는 스팀 대사 18,271행 TSV. 주요 규칙:

  • 정확히 일치하는 대사는 스팀 KR 그대로 채택, 미일치분은 스팀 어조로 새로 번역.
  • 바이트 예산으로 줄일 때도 어조를 살려 자연스럽게 축약.
  • 문단이 안 바뀌면 줄을 최대한 채운다(그리디 워드랩이 자동 보장).
  • 전각 구두점(。、！？…) 뒤에는 공백을 넣지 않는다(구두점 자체에 여백 포함).
  • 고유명사·지명·인명은 스팀 기준으로 통일. 캐릭터 메이킹 퀴즈만 별도 공략 참고.

6.2 처리 흐름

원본 SCEN 추출 → MTE 전개(mte_expand) → 스팀 정확매치 채택(steam_adopt) → 퍼지매치(≥0.95) → 미매치 병렬 워크플로 재번역 → render() 조판(14칸·페이지·반각공백) → 정렬보존 리빌드 → 디스크 in-place 기록

번역문은 flat 텍스트(어절 공백만)로 두고 조판(render())이 워드랩·페이지·{01}·{08}를 자동 삽입 — 번역과 조판을 분리해 규칙 변경 시 일괄 재조판이 가능합니다.

7.4 병종(클래스)명 — 전투 준비/정보 화면

병종명은 압축 이미지가 아니라 반각 카타카나 텍스트 + 변환 테이블임을 라이브 디버깅으로 규명했습니다. (검증: 테이블의 ｸﾞﾗﾃﾞｨｴｰﾀｰ 자리를 ﾀﾏﾈｷﾞｰ로 덮었더니 화면 병종명이 그대로 바뀜.) 렌더 경로:

반각 카타카나 문자열 → 변환기(idx=(byte+0x60)&0xFF → 2B BE SJIS) → 표준 텍스트 엔진 + FONT.DAT(한글 폰트) → 화면

코드 훅 없이 데이터 세 곳만 다시 씁니다(gen_classnames):

데이터위치(LANG2.BIN)처리
병종명 문자열 테이블≈ 0x62218카타카나 → 한글 인덱스 바이트로 교체
포인터 테이블0x619dc새 한글 문자열 주소로 재지정
변환 테이블0x6388c인덱스 → 한글 전각 SJIS 코드로 재작성(빈 공간으로 이전)

변환기가 한글 인덱스 바이트를 한글 SJIS 코드로 바꾸고, 기존 텍스트 엔진이 그 코드를 FONT.DAT의 한글 글리프로 렌더합니다. 실기 검증: 유닛 정보 패널의 엘윈 / 워록 / 보병 클린 한글 렌더 확인(Ep2 129병종 / 142음절).

참고 — 왜 SCEN 치환이 안 먹혔나: 초기에 SCEN.DAT의 클래스명을 2만여 건 치환했는데 화면에 반영되지 않았습니다. 렌더 소스가 SCEN이 아니라 바로 이 반각 카타카나 테이블이었기 때문입니다. "어디서 읽어 그리는지"를 라이브로 특정한 것이 결정적이었습니다.

8특수 사례 — 로드창 시나리오 제목

로드/세이브 창의 시나리오 제목("서장" 등)이 깨진 세로줄(dither)로 나오는 난제가 있었습니다. 대사·정보패널 폰트 경로와 별개의 프론트엔드 렌더 경로를 쓰기 때문으로, 라이브 디스어셈블·브레이크포인트·레지스터 추적으로 근본 원인을 규명했습니다.

근본 원인 (2층 구조)

  1. 파싱 붕괴: 로드창 템플릿은 面{01}0e【{02}】 형태인데, 원본 {01}은 "소스 1바이트 소비" 핸들러입니다. KR 빌드가 {01}을 반각 공백(소스 미소비)으로 패치하면서(5.1) 템플릿의 0e가 문자로 누출돼 dither가 발생.
  2. 동적 제목 재귀 렌더 크래시: {02}(제목 삽입) 핸들러가 참조하는 레지던트 제목 구조가 불투명해 빌드 측 데이터 수정으로는 안정적으로 고칠 수 없음(재귀 렌더가 오정렬 포인터로 폭주 크래시).

배송한 해결 (데이터-only)

크래시하는 동적 제목 템플릿을 버리고, 템플릿 A/B를 {03}(시나리오 번호, 세이브별 정확) + 장(한글 직접 글리프)로 교체했습니다. 결과적으로 로드창이 "N장"을 dither·크래시 없이 클린 한글로 렌더합니다(콜드부트 검증 완료). 실제 시나리오명 표시는 프론트엔드 재구조화 역공학이 필요해 트레이드오프로 남겼습니다.

9검증 방법론

  • 라이브 RAM 검증: emucap으로 실행 중 RAM/VRAM에 글리프·문자열을 직접 write해 화면 변화를 관찰 → "어느 데이터가 어느 화면을 그리는지"를 실증(병종명 테이블·변환기 위치 등이 이렇게 확정됨).
  • 콜드부트 검증: 재빌드 후에는 반드시 에뮬레이터를 완전 재기동(PID kill + launch)해 검증합니다. reset은 로드된 게임을 유지하고, 세이브스테이트는 재빌드 시 폰트 슬롯이 어긋나 스테일 아티팩트를 유발하므로 콜드부트 픽셀 검증이 정본입니다.
  • 세이브 데이터 키잉 주의: Mednafen 백업RAM은 디스크 콘텐츠 해시별로 분리 저장돼, 재빌드하면 해시가 바뀌어 세이브가 사라집니다. 로드창 검증 시 옛 세이브를 새 디스크 해시 파일명으로 복사해 주입합니다.
  • 레이어 격리: VDP1 스프라이트 / VDP2 NBG 레이어를 토글해 텍스트가 어느 하드웨어 레이어에 그려지는지 특정.
