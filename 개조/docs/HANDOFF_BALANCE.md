## 📌 세션 종료 시점 상태

SH-2 코드 패치 방법론" 참고 — **다음에 또 코드 레벨 버그를 찾아야 하면 이 부록부터

"이번 세션 밸런스 변경 내역"을 정본으로 본다(계획 문서는 사후 갱신 안 함 — 실제

  해석해 A_mod/D_mod 단조증가를 기대하는 감사 방법을 시도했다가 폐기함** —

  단순 "승급 트리"가 아니라 다른 의미(용병 재배치·팔레트 변형 등)일 가능성이 높다

  계열(로드/마스터 등) 직접 비교" 방법이 훨씬 신뢰도 높았다.

## ✅ 세션2 후반 추가: 크라운 패치 완성판 + L1 오프셋 신규 발견

**최종 배포물**: `build/Langrisser I&II Dramatic Edition (KR v1.2).chd` — 내용:
크라운 경험치 2배(L1·L2 모두), 시나리오1 상점에 크라운+룬스톤 추가(L1·L2),
크라운·룬스톤 가격 10P(L1·L2), **크라운 4번 슬롯에 마법내성+20 추가(L1·L2)** —
아이템 마법내성 효과는 부대(용병)에도 적용됨을 사용자가 아뮬렛으로 실기 확인.
밸런스 JSON 변경분은 `item_l2.json`(크라운·룬스톤 price=1, 크라운 effects 슬롯4=
magic_resist+20)과 `shop_l2.json`(상점0 슬롯=[1,33,35,0] — 스몰실드 제거)에만 있음
— L1 쪽은 registry 미등록이라 bin_region 직접 패치(상점0 0x64354~7, 가격 +64/+68,
크라운 효과 슬롯4 = 효과테이블 0x60a68+32*16+12 에 `00 08 00 14`).

⚠ **상점 테이블은 0 종료 방식이다** — 상점0의 4슬롯을 다 채웠더니 실기에서 다음
상점(나이프·로브)까지 이어 표시됐다. 각 상점은 마지막 슬롯을 0으로 남겨야 한다
(`shop_dat.py` docstring에도 기록). 그래서 상점0에서 스몰실드를 빼고 3개+0으로 맞췄다.

**경험치 2배 코드는 실제로 3지점이다**(세션2 초반 "2지점"은 오탐 — 세 번째를
실기 테스트 실패로 발견): 비교값(11→33)과 **읽는 슬롯(add #72→#73: 무기→장비
아이템2)** 둘 다 고쳐야 크라운(악세서리류)이 인식된다. 실기 검증 완료(사용자 확인).

| 대상 | L2 (LANG2.BIN) | L1 (LANG1.BIN, 세션2 신규 발견) |
|---|---|---|
| 코드 site1 (slot imm / cmp imm) | 70505 / 70511 | 0xf6bd / 0xf6c3 |
| 코드 site2 | 70707 / 70713 | 0xf787 / 0xf78d |
| 코드 site3 | 72599 / 72605 | 0xfee7 / 0xfeed |
| 아이템 효과 테이블(35×16B) | 397276 | **0x60a68** |
| 아이템 가격 테이블(35×2B BE) | 413750 | **0x644aa** |
| 상점 테이블 | 413004 (276B, 27상점) | **0x64354** (~342B, 상점 수 미확정) |

L1도 아이템 35종·가격·효과가 L2와 완전 동일(엔진 공유). L1 크라운도 원래 일반
상점 판매 없음(끝의 치트상점 2개에만) — L2와 같은 구조. L2 크라운의 정상 입수처는
적 지휘관 5명뿐(시나리오21·65·65·70·70, stage_l2.json 실측).

⚠ L1 상점 테이블은 경계(상점 수/그룹)를 아직 안 풀었다 — 상점0(선두, 나이프+
스몰실드)이 시나리오1인 것만 유추 확정. 다른 L1 상점을 고치려면 경계 분석 먼저.

### 다시 빌드해야 할 일이 생기면

```powershell
$env:PATH += ";C:\Program Files\dotnet"
cd "C:\Project\Lang KR rom edit\DerEditor_V1.9.1\decompiled"
dotnet build
# 결과: bin\Debug\net8.0-windows\DerEditor.exe
```

**⚠ 미리 알아야 할 것:**
- `.NET 8 SDK`가 이번 세션에 새로 설치됨(`winget install Microsoft.DotNet.SDK.8`).
  경로: `C:\Program Files\dotnet`.
- `DerEditor.csproj`의 `TargetFramework`를 원래 디컴파일된 값 `net20`에서
  **`net8.0-windows`로 이미 바꿔놨다**(되돌리지 마라) — `net20`은 최신 SDK로 빌드하면
  `ResGen.exe not supported on .NET Core MSBuild` 에러가 난다. 프레임워크만 바꿨고
  동작은 정상 확인됨(WinForms 코드가 순정 .NET Framework 2.0 API만 써서 호환됨).
- 빌드 중이던 예전 exe가 **다른 세션(인터랙티브 데스크톱, SessionId 1)에서 실행 중이면
  taskkill/Stop-Process가 "Access is denied"로 실패**한다(자동화 세션 권한 밖). 그래도
  `dotnet build`는 보통 성공했다(락이 안 걸리는 경우가 있는 듯) — 실패하면 사용자에게
  DerEditor 창을 닫아달라고 요청해라.
- 경고 9,700여 개(`CA1416` 플랫폼 호환성 경고)는 **정상**이다 — Windows 전용 앱을
  cross-platform SDK로 빌드해서 나오는 노이즈, 무시해도 됨.

## 부록: SH-2 코드 패치 방법론 (세션2에서 확립)

데이터 테이블(class_dat 등)로 안 되는 하드코딩된 게임 로직(예: 특정 아이템의
경험치 배율)을 고치려면 결국 SH-2 실행 코드를 직접 찾아 패치해야 한다. 세션2에서
"메샤이얀소드 경험치 2배" 로직을 찾아 패치하기까지의 과정을 정리한다.

### 0) `Next/original/` 이 비어있을 수 있다

gitignore된 세션 산출물이라 새 세션에서 없을 수 있다. 없으면 원본 디스크에서
11개 파일을 다시 뽑는다(0.BIN, LANG1.BIN, LANG2.BIN, LANG{1,2}/{SCEN,FONT,IMG,
CLASS}.DAT) — `disc_files.find()` + `Disc.read_file()`로 간단히 재현 가능,
`README.md` 3절에 정확한 파일명 표가 있다.

### 1) emucap MCP 서버가 세션에 등록만 되고 재시작이 안 됐을 수 있다

`claude mcp add emucap-control -s user -- <경로>/emucap-mcp.exe` (+ emucap-track)로
**user 스코프**로 등록해야 어느 프로젝트 디렉터리에서 시작하든 잡힌다(local
스코프로 잘못 등록하면 emucap 프로젝트 폴더에서만 보임). 등록 후 **VSCode
세션을 재시작**해야 도구가 실제로 로드된다.

### 2) Windows에서 emucap의 `launch` MCP 툴(Rust 크로스플랫폼 런처)이 즉시 죽을 수 있다

`launch()`를 부르면 `emulator_process_state: exited`로 즉시 실패하는데
`mednafen.log`는 0바이트 — 이 환경(Windows, 이번 세션 기준)에서 재현된 버그다.
**우회법**: `adapters/mednafen/work/mednafen/src/mednafen.exe`를 Bash
`run_in_background`로 직접 실행하되, 다음 환경변수를 반드시 세팅한다(이게 없으면
그냥 독립 에뮬로 뜨고 emucap에 안 잡힘):
```
EMUCAP_PORT=<status.listening_port>
EMUCAP_NAME=<아무이름>
EMUCAP_CONTENT=<cue 절대경로>
EMUCAP_SESSION_TOKEN=<토큰파일 내용>
```
토큰 파일 경로는 `status.identity_guard.session_token_file.path`
(보통 `%TEMP%\emucap_session_token_<port>`). **★★ 토큰은 `status`/`bootstrap`을
호출할 때마다 회전(rotate)한다** — 토큰을 미리 읽어놓고 한참 있다가 실행하면
mismatch로 조용히 실패(연결 자체가 안 잡힘, occupant도 안 뜸)한다. **토큰을 읽는
동작과 mednafen.exe 실행 사이에 다른 `status`/`bootstrap` 호출을 끼우지 말 것** —
읽자마자 바로 실행해야 한다. 성공하면 `sleep 6` 정도 후 `status`가
`connected:true`를 반환한다.

### 3) 라이브 코드 위치 찾기 — before/after 메모리 diff는 노이즈가 너무 크다

워크램(workramh, 1MB)은 사운드·애니메이션·RNG 상태가 매 프레임 바뀌어서 몇 초
창으로 diff해도 변경 후보가 수백 개 나온다 — 이 방법은 사실상 못 쓴다. 대신:

1. **알려진 단서를 최우선으로 활용해라.** 이번 세션엔 사용자가 액션리플레이 치트
   코드(`3609CE0A 00FF`)를 갖고 있었다 — 상위 니블(코드타입)을 걷어내면
   `0x09CE0A`가 workramh 오프셋으로 바로 나왔고, 실제 전투 전/후 diff에서 그
   주소가 변한 걸 이미 확보하고 있었다. **AR/PAR 치트 코드가 하나라도 있으면
   그게 가장 빠른 진입점이다.**
2. 단서가 없으면 알려진 필드(`character_dat.py`의 EXP 등)를 참고해 struct 후보를
   추정하되, **"주변 바이트가 그럴듯해 보인다"만으로 확신하지 말 것** — 이번
   세션에 AT=19/DF=18 매칭 struct를 EXP struct로 잘못 짚었다가(사실 UI 아이콘
   룩업 테이블이었음) 시간을 꽤 썼다.
3. 정확한 주소를 알면 `set_breakpoint(kind="write", memory_type="workramh",
   start=주소, end=주소, pause_on_hit=true)` → `tap(["a"])` → `run_frames(N)`으로
   실전투를 트리거해 히트시킨다. `poll_events()`로 히트 당시 `pc`(SH-2 프로그램
   카운터)를 얻는다 — **이게 진짜 목표**(주소 자체보다 "누가 거길 쓰는가"가 중요).
4. `disassemble(address=pc-여유바이트, count=40~80)`으로 히트 지점 앞뒤를 넓게
   본다. SH-2는 명령어가 고정 2바이트라 자르기 쉽다 — 단, **`rts`(함수 반환)를
   만나면 그 위가 다른 함수일 수 있다**(실제로 겪음, 함수 경계를 잘못 넘어가서
   엉뚱한 코드를 "그 함수의 일부"로 착각할 뻔함).
5. 아이템ID 체크 같은 조건 분기는 보통 `extu.b rX,rY` (바이트 로드) →
   `cmp/eq #imm,rX` → `bf/bt disp`(조건분기) 패턴이다. `imm` 값이 `item_dat.py`의
   아이템 인덱스와 일치하는지 대조하면 확증된다.

### 4) RAM 주소 → 디스크 파일 오프셋 변환

패치는 디스크(LANG2.BIN)에 영구 반영해야 하므로 RAM 주소를 파일 오프셋으로
바꿔야 한다. **직접 계산하지 말고 실측해라**: 대상 명령어의 raw 바이트 4~6개를
`find_pattern`(라이브 RAM) 또는 파이썬으로 뽑아, `Disc.read_file()`로 읽은
LANG2.BIN 원본 바이트열에서 **같은 바이트열을 검색**하면 파일 오프셋이 바로
나온다(이번 세션: RAM `0x0602136E` → 파일 오프셋 `70510`, 즉 로드베이스가 정확히
`0x06010000`이었다 — 항상 이렇게 깔끔하진 않을 수 있으니 검색으로 확인하는 게
안전하다). **매치가 2개 이상 나오면** (이번 세션엔 동일 로직이 공격측/피공격측
2군데 복제돼 있어서 2개 나왔다) 라이브 디스어셈블로 각각의 문맥을 확인해서 전부
찾아 전부 패치해야 한다 — 하나만 고치면 절반만 고쳐진다.

### 5) 패치 전 반드시 "이 구간이 원본과 한글화 빌드에서 바이트 동일한지" 확인

한글화가 `LANG*.BIN` 곳곳(반각공백 패치·카타카나 리다이렉트·병종명 케이브 등)을
건드려놨다. `Next/original/`(원본)과 방금 만든 `build/disc-krpoc/track1.bin`(KR
패치본)에서 대상 파일 오프셋 구간을 각각 읽어 바이트 비교 — 동일하면 안전하게
같은 오프셋에 패치해도 된다. 다르면 그 구간이 한글화 자산일 가능성이 크므로
더 조사해야 한다.

### 6) `apply_balance.py`가 다루지 않는 임의 바이트 패치는 `bin_region.write_region()`로

`write_region(disc, "LANG2.BIN", 파일오프셋, payload_bytes)` 하나면 된다 —
파일 전체를 read-modify-write하고 EDC/ECC를 자동 재계산한다. `registry.py`에
등록 안 된 1회성 코드 패치엔 이걸 직접 쓰면 되고, 매번 자동 반영해야 하는
정식 테이블이 되면 그때 `registry.py`에 등록해 파이프라인화하면 된다.

### 7) 빌드 순서 — `rebuild.py`가 밸런스 변경을 덮어쓴다

`rebuild.py`는 `Next/original/` + 워크시트에서 `build/disc-krpoc/track1.bin`을
**처음부터 다시** 만든다. 즉 `apply_balance.py`(또는 수동 `write_region`)로 넣은
변경사항은 `rebuild.py`를 나중에 돌리면 전부 사라진다. **순서를 반드시
지켜라**: `rebuild.py`(한글화 베이스) → `apply_balance.py`/코드패치(밸런스) →
필요시 `chdman`. "되돌리고 싶다"는 요청이 오면 `rebuild.py`만 다시 돌리면
깨끗한 한글화 베이스로 복귀한다(밸런스 변경은 JSON에 남아있으니 나중에
`apply_balance.py`만 다시 돌리면 복원 가능).
