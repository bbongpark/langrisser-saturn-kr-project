# 밸런스 패치 파이프라인 — 전체 탭 완료

**작성 2026-08-02.** 한글화 완료 후 롬 개조(밸런스 패치) 착수 세션. `DerEditor_V1.9.1`
(중국 팬패치 에디터) 디컴파일로 **12개 탭 전부를 조사**했고, 그중 **11개 탭을 실제
읽기/쓰기 파이프라인으로 완성**했다(전부 실제 디스크 데이터로 검증, 라운드트립
바이트 단위 일치 확인). 남은 1개는 SS(새턴)판에 아예 없는 기능(탭7)이라 조사만
하고 끝났고, 1개(탭12)는 데이터 테이블이 아니라 성격이 달라 이 파이프라인
범위 밖이다 — 즉 **"데이터 테이블"인 탭은 전부 완성됐다.**

## 2. 사용법

```bash
cd Next/scripts/balance
python extract_balance.py     # registry.py에 등록된 10개 고정오프셋 테이블을 JSON으로
python extract_stage.py       # + 스테이지 92개(SCEN.DAT, 별도 CLI — 아래 참고)
# build/balance/*.json 편집
python apply_balance.py       # 고정오프셋 테이블 반영 (같은 크기만, EDC/ECC 자동 재계산)
python apply_stage.py         # 스테이지 반영 (SCEN.DAT 전체 재조립, 크기 불변 검증)
```

### 왜 스테이지 데이터만 별도 CLI인가

다른 테이블은 "파일의 고정 오프셋 구간"이지만, 스테이지 유닛 배치는 **SCEN.DAT
안에 압축돼 있고, SCEN.DAT 자체가 대사 텍스트와 같은 가변길이 트리 구조**(`scen_tool.py`,
한글화가 이미 검증한 파서)라 다른 종류의 파이프라인이 필요하다 — 8절 참고.

`registry.py`가 테이블 목록의 정본이다 — 파일 경로·오프셋·크기·코덱 모듈을
한곳에 모아둔다. 새 테이블을 풀면 여기 한 줄 추가하면 extract/apply가 자동으로
같이 처리한다.

### 아키텍처

```
disc_tool.py      저수준: LBA 단위 read_file/write_file + EDC/ECC 재계산 (kr-patch 원작)
disc_files.py     ISO9660 파일명→LBA 파서 (이번 세션 신규)
bin_region.py     "파일 하나 안의 한 구간"을 read-modify-write (이번 세션 신규,
                   CLASS.DAT처럼 파일 전체가 테이블이든 LANG2.BIN 안 일부 구간이든
                   동일하게 다룬다 — 구간 밖 바이트는 절대 안 건드림)
json_io.py        공통 JSON 로드/저장
{class,fight,magic,item,character,shop,terrain,matchup}_dat.py
                   테이블별 decode(bytes...)→레코드 / encode(레코드)→bytes... 코덱
registry.py        테이블 목록 (파일경로·오프셋·크기·모듈)
extract_balance.py / apply_balance.py   registry.py를 순회하는 CLI
```

### 종단 검증 (이번 세션 실행함)

**등록된 10개 테이블 전부**를 디스크에서 추출 → 수정 없이 그대로 재반영 →
**392MB 디스크 전체를 원본과 바이트 diff → 차이 0바이트.** 각 모듈의
`decode(encode(x)) == x` 자체 테스트도 전부 통과. CLASS.DAT 한 필드를 실제로
바꿔본 첫 세션 테스트(32바이트만 변경, EDC/ECC 정상)도 여전히 유효하고,
`promotion_dat.py`도 실제 데이터로 슬롯 하나만 편집해 정확히 1바이트만
바뀌는 것까지 확인했다.

## 3. 각 테이블 요약 (자세한 필드표는 각 .py 파일 docstring 참고)

### class_dat.py — 병종/직업 스탯
`LANG1|LANG2/CLASS.DAT` 7,140B = 255레코드×28B. 마력·AT·DF·MV·지휘범위·A/D수정치·
MP·마법내성·용병수/가격·처치골드/경험치·마법슬롯4개. **L1도 검증됨**(구조 동일,
초반 병종이 L2와 바이트 단위로 거의 일치).

### fight_dat.py — 공격 방식
`LANG1|LANG2/FIGHT.DAT` offset 91부터 2040B = 255레코드×8B. 점유폭/높이(지도 위
스프라이트 크기), 대공/대지 공격력. CLASS.DAT과 같은 인덱스(레코드 i = 같은 병종).

### magic_dat.py — 마법
`LANG2.BIN` offset 397016, 104B = 26레코드×4B. 사거리·필수타겟 여부·파급범위·
MP소모·대상진영(적/아군). 공격계=전부 적방, 회복계=전부 아군으로 완벽히 일관됨.
⚠ L1 오프셋 미검증.

### item_dat.py — 아이템/장비
`LANG2.BIN` offset 397276(효과,560B)+413750(가격,70B) = 35레코드. 효과슬롯 4개
(종류: AT/DF/MV/지휘범위/A수정/D수정/마법사거리/마법위력/마법내성/소환) + 가격.
⚠ 장비가능 병종 제한(bytes17)은 **SS판에 아예 없음**(PS1 전용 확인). L1 미검증.

### character_dat.py — 등장인물(18명) 초기 스탯
`LANG2.BIN` offset 397200(보정,72B)+400432(초기상태,360B) = 18레코드. 초기 직업·
LV·MP·AT·DF·경험치·습득마법(32비트 플래그)·성별·초상화·용병. **DerEditor 원본은
72B 중 54B만 읽고 72B를 되써서 마지막 3명 데이터를 저장 시 파괴하는 버그가 있다
— 이 프로젝트의 코덱은 그 버그를 재현하지 않는다**(항상 72B 전체를 온전히 다룸).
⚠ L1 미검증.

### shop_dat.py — 상점
`LANG2.BIN` offset 413004, 276B = 27개 상점(가변길이 슬롯, 4~36개). 각 슬롯 =
파는 아이템 인덱스(0=없음). **슬롯 개수 자체는 못 늘림**(파일 크기 고정) —
어떤 아이템을 파는지만 바꿀 수 있다. 마지막 2개는 "商店秘籍"(디버그용 전체상점).

### terrain_dat.py — 지형
`LANG2.BIN` offset 397836(이동력,1044B)+395808(지형고유방어,29B)+406502(병종별
지형방어,522B). 지형 29종 × 병종 18종. 이동력은 **2바이트 중 홀수바이트만
SS가 쓴다**(짝수는 타 플랫폼용, 코덱이 그대로 보존). 255=이동불가.

### matchup_dat.py — 병종 상성
`LANG2.BIN` offset 405854, 648B = 18×18, 셀마다 (공격%가산, 방어%가산). 엑소시스트
(退魔类) 행이 슬라임/악마/유령/언데드에 집중 보너스 — "대언데드 특화" 컨셉과 일치.

### stage_reward_dat.py — 스테이지 클리어 보상
`LANG2.BIN` offset 405656(골드×10,92B)+405756(경험치,92B) = 92스테이지. 탭9의
일부지만 고정길이라 독립적으로 완성했다.

### promotion_dat.py — 전직(승급) 트리
`LANG2.BIN` offset 398880부터 1,029B(승급슬롯 956B + 바로 뒤 포인터테이블 72B)
= 18명, 슬롯 11~19개(2명은 0개). **레코드 순서가 캐릭터 순서와 무관**하고
(포인터로만 위치 특정) **슬롯 개수도 제각각**이라 "raw 전체 블롭 + 슬롯만
덮어쓰기" 방식으로 안전하게 만들었다 — 슬롯이 어디서 끝나는지는 다음 포인터가
아니라 **`FFFFFFFF` 종료자**로 판별한다(18명 전원 실측 확인). 슬롯 4바이트 =
[예비][소스병종+1][팔레트][타깃병종ID] — **타깃병종ID만 바꾸면 그 병종이
승급 시 어떤 병종이 되는지 바뀐다**, 밸런스 튜닝에 바로 쓸 수 있다.
⚠ **`bytes7`(체크포인트/전직메뉴 표시용 목록)은 다루지 않는다** — bytes8과의
관계(단순 UI 캐시인지 게임 로직도 참조하는지)가 미확인이라, 여기만 바꿔서
실기 테스트 후 전직 메뉴에 문제가 있으면 그때 봐야 한다. 슬롯 **개수**는
못 바꾼다(내용만 편집 가능).

### stage_dat.py + langr_compress.py — 스테이지별 유닛 배치 (탭9)
`LANG2/SCEN.DAT` 안, 92개 스테이지 각각 압축된 블롭(`scen_tool` 트리의
`children[i].children[1]`). `langr_compress.py`가 이번 세션에 새로 짠
압축기(디코더는 이식, 인코더는 신규 — 92개 실측 검증). 유닛 레코드(44B/유닛)의
item/AI/진영/좌표/LV/EXP/MP/MAXMP/AT/DF/캐릭터ID/병종ID/초상화를 다룬다.
자세한 내용·안전장치는 4절 참고. **일반 `registry.py` 파이프라인과 별도
CLI**(`extract_stage.py`/`apply_stage.py`)로 돈다 — SCEN.DAT 전체를
`scen_tool`로 재파싱/재조립해야 해서다.

## 4. 조사했지만 파이프라인 미완성 — 다음 세션 과제

### 탭6 "转职数据" (전직 트리) — bytes8(실제 승급표)만 구현, bytes7은 미구현
- `promotion_dat.py`가 `bytes8`(offset 398880,956B, 4B/슬롯: [+0]예비
  [+1]소스클래스+1 [+2]팔레트 [+3]타깃클래스ID)을 다룬다 — **종료자
  (`FFFFFFFF`) 기반이라 포인터 순서가 뒤섞여 있어도 안전**하다(2절 참고).
- `bytes7`(offset 413824,484B, 캐릭터별 승급 "체크포인트" 목록, **가변길이 —
  포인터 `iAddr7[i]`=414337+i*4의 3바이트 빅엔디안−479360**)은 **아직 손 안
  댔다**. bytes8과 데이터가 겹쳐 보이는데 정확한 관계(단순 UI용 캐시인지,
  게임이 실제로 이걸 읽어 승급 메뉴를 그리는지)를 몰라서 안 건드리는 게
  안전하다고 판단했다 — bytes8만 바꿔 실기 테스트 후 필요하면 여기도 볼 것.
- Elwin(idx=0)은 다른 18명과 레이아웃이 다른 특수 레코드(4갈래 분기, 19슬롯) —
  `promotion_dat.py`는 이것도 정상적으로 (일반 캐릭터와 같은 방식으로) 다뤘지만
  그 4갈래가 정확히 뭘 뜻하는지(시나리오 분기?)는 미해독.

### 탭9 "关卡数据" (스테이지 92개) — 완료
`stage_dat.py` + `extract_stage.py`/`apply_stage.py`(별도 CLI, 위 2절 참고).
92개 스테이지 전부 실제 디스크 데이터로 검증(round-trip 무편집 시 디스크
전체 diff 0바이트, 실제 필드 편집 시 딱 1섹터만 EDC/ECC 포함 정상 변경 확인).

**압축 문제를 어떻게 풀었나:**
- SCEN.DAT의 커스텀 LZ 압축(`Compression` 클래스)의 **디코더**는 조사 세션이
  이식했고, **인코더(압축기)는 이번에 새로 작성**했다(`langr_compress.py`) —
  decode(encode(x))==x를 **92개 실제 스테이지 블롭 전부**로 검증했고, 압축률도
  원본과 같거나 더 좋다(실측: 92개 전부 원본 이하 크기, 합계 0.96x).
- SCEN.DAT는 `scen_tool.py`(대사 텍스트가 사는 그 재귀 트리 파서, 한글화가
  이미 수없이 검증함)로 다룬다 — 스테이지 i의 압축 블롭은 정확히
  `tree.children[i].children[1]`(실측 확인)이라 그 리프의 `raw`만 바꾸고
  `scen_tool.serialize()`를 부르면 SCEN.DAT 전체 오프셋이 자동으로 재계산된다.
- **SCEN.DAT 총 크기는 고정**(디스크에 같은 크기로만 패치 가능)이라, 새로
  압축한 스테이지는 **원본 압축 크기에 맞춰 0바이트로 패딩**한다 — 압축
  스트림이 종료 마커로 끝나고 디코더가 그 이후를 안 읽으므로 안전하다(마커
  다음에 뭘 붙이든 무시됨). 패딩으로도 못 줄이면(원본보다 커지면) 에러를 내고
  디스크에 안 쓴다.
- **실제로 편집한 스테이지만** 원본 압축 바이트를 교체한다(`stage_dat.unchanged()`가
  압축 해제한 내용을 비교) — 안 건드린 스테이지는 원본 바이트 그대로 남아
  디스크 변경 범위가 최소화된다.

**다룰 수 있는 필드**: item1/item2, activity(AI 행동적극도), cmd(지령),
faction_raw(진영), atk_target, dest_x/y, chr_target, LV/EXP/MP/MAXMP/AT/DF,
pos_x/y(배치좌표), name_id, class_id, portrait — 스탯·장비·AI·배치 전부 편집
가능. `stage_dat.py` docstring의 표에 ★ 표시된 필드가 신뢰도 높은 것들이다.

**유닛 개수는 못 바꾼다**(값 편집만) — 헤더/캐릭터목록/지휘관좌표 구간도 안 바꾼다.

**여전히 미해독**: 유닛 레코드의 +10(행동코드), +16,+26,+29~30,+32~43 일부

순 있지만 효과는 모른다 — `button23_Click`/`button24_Click`(Form1.cs
8075·8464행)저장 로직을 더 읽으면 풀릴 가능성이 높다.

### 탭12 "黑科技" — 데이터 테이블이 아니라 패처, 이 파이프라인 범위 밖
버그수정/확장기능을 온오프하는 바이너리 패치 모음(`groupBox3/4/5`). 정상적인
"수치 조정"이 아니라 "기능 켜고 끄기"라 밸런스 데이터 파이프라인과 성격이 다름 —
필요해지면 별도로 다룰 것(`LoadBlackTech()`/`button28_Click`, Form1.cs ~8736·1829행).

### 공통 미확인 사항
- **L1(랑그릿사1) 오프셋은 magic/item/character/shop/terrain/matchup 전부
  미검증이다** — CLASS.DAT·FIGHT.DAT만 L1도 확인했다. DerEditor 자체가 SSL1을
  지원 안 해서 L1은 참고할 UI가 없다 — L1도 필요해지면 LANG1.BIN에서 CLASS.DAT
  세션처럼 "값이 말이 되는지"로 오프셋을 직접 찾아야 한다(구조는 L2와 같을
  가능성이 높다, 세션1 확인).
- 각 테이블의 ID류 필드(병종 type, merc/magic ID 등)는 전부 **RAW 값만** 보존한다
  — 어떤 숫자가 어떤 이름인지 매핑하는 문자열 테이블은 안 풀었다. 값을 바꿀 땐
  같은 게임의 다른 레코드가 이미 쓰는 ID를 재사용하는 게 안전하다.

## 5. kr-patch 파이프라인과의 관계

**한글화 파이프라인은 손대지 않았다.** `Next/scripts/balance/`는 전부 신규 파일이고
기존 `rebuild.py` 3단계 다음에 얹는 구조다:

```
python scripts/rebuild.py                    # 기존: 한글 텍스트 패치
cd scripts/balance && python extract_balance.py   # 신규: 밸런스 데이터 추출
# ... JSON 편집 ...
python apply_balance.py                       # 신규: 같은 디스크에 밸런스 반영
```

CLASS.DAT·FIGHT.DAT·LANG2.BIN 데이터 구간은 한글화가 건드리지 않은 영역이라
순서를 바꿔도 되지만, **LANG*.BIN 꼬리(병종명 케이브 등 한글화 자산)와 겹치지
않으므로 안전**하다는 걸 이번 세션에 오프셋 표로 재확인했다. 항상 `rebuild.py`
다음에 밸런스 단계를 돌리는 습관을 들이면 된다.
